What will be discussed

1. Conformance profiles: remove `requirements/` folder; organize semantically.

PR #12

ARCH-ADR-7 · branch fix/conformance_profiles_folder_re-structuring

  • A specification's functionalities are grouped into conformance profiles: one core, which every conformant software solution meets, and extenchannel-namesions a solution may claim on top of it.
  • requirements/ becomes conformance-profiles/, with one folder per profile, holding an introduction.md and a functionalities/ folder. The folder name is the profile id.
  • Each profile is declared in the front matter of its introduction.md. metadata.yml no longer lists extensions, and functionality files no longer carry conformance or extension.
  • The Technical Overview gets shorter: one table of profiles, example conformance claims, and how profiles divide the capabilities. Functionalities, actors and interfaces move to each profile's introduction.
  • The Wallet worked example is removed and replaced with an abstract Building Block that every example now uses.

To settle

  • One core plus extensions as profile types, instead of profiles with no special core
  • The folder name as a permanent id: renaming a profile folder is not allowed
  • The compiler change: toc.yml subsections under conformance-profiles

2. Bringing back optional requirements and add conditionality

PR #2

ARCH-ADR-6 · branch feat/requirement_optionality

  • A variation point is a requirement that a solution meets by meeting at least a given number of its options, such as "accepts at least one of these credential types". It cannot be skipped.
  • Options get a new level, OPTION, are listed beneath their variation point, and are numbered n.m (requirement 30 has options 30.1, 30.2…).
  • Conditional requirements apply only when a solution meets a given option or claims a given extension, through applies_when, so tests and GovMarket report them as not applicable rather than failed.
  • An option can be met by claiming an extension, for choices that bring a whole protocol stack with them.

To settle

  • The six questions at the end of the ADR: publishing an option as a minor change, options met by claiming an extension, numbering of options added later, requirements that relate two variation points, extensions that need an option, and whether max is needed

Overlap with PR #12: ARCH-ADR-6 still places extensions in metadata.yml and functionalities in requirements/. If PR #12 is accepted, ARCH-ADR-6 needs to follow its layout. We will agree the merge order.

3. Removing the observability classifier

PR #13

ARCH-ADR-8 · branch feat/remove_observability_classifier

  • Building Block specifications stop setting observability. How a requirement is verified follows from its interaction: INTERNAL is audited against evidence, and every other type is tested at its boundary.
  • In the Document Management draft, 146 of 150 requirements already follow this rule, and the other four are classification slips.
  • The cross-functional requirements keep observability, because they carry no interaction.

To settle

  • The narrower meaning of INTERNAL: only what cannot be seen at any boundary
  • Whether the cross-functional requirements should adopt interaction later
  • Moving a requirement to or from INTERNAL as a minor release
